# PROTOCOL.md — предрегистрация независимого аудита RASM-CIM (кореференция)

Автор протокола: независимый аудитор (Arena Agent, роль «аудитор/исследователь»).
Дата: 2026-11-27. Ветка аудита: `arena/ec75e510-bunyod`, база `47cba72` (main).
Этот файл создан и закоммичен **до** создания наборов и **до** любого прогона
системы на новых данных. Хеш коммита и sha256 файла фиксируются в
`REPORT_INDEPENDENT.md`; если после запуска протокол менялся — это будет
указано отдельно, с причиной.

Заявления авторов, взятые из `docs_v17/COREF_REPORT.md` и `docs_v17/PROGRESS.md`

## 2. Наборы (создаются после коммита протокола)

Все наборы написаны вручную как диалоги на естественном языке, **без
генератора**; в каждом кейсе автор, дата и метод разметки записаны в самом
файле.

| Набор | Файл | n (план) | Назначение |
|-------|------|----------|------------|
| A. Связка | `audit_v1/data/bind.jsonl` | 70 | верный ответ — связать местоимение с названным объектом |
| B. Переспрос | `audit_v1/data/refuse.jsonl` | 50 | верный ответ — переспросить (нет антецедента, два равных кандидата, не тот род, «они» о группе) |
| C. Смешанный «живой» | `audit_v1/data/mixed.jsonl` | 45 | разговорная речь, опечатки, неполные фразы, русский с таджикскими словами, длинные диалоги (8+ реплик); внутри есть и связки, и переспросы |
| D. Hidden | `audit_v1/data/hidden.jsonl` | 60 | запечатан до финального прогона (sha256 фиксируется сразу после создания) |
| E. Переформулировки | `audit_v1/data/paraphrase.jsonl` | ≥ 55 | другой формулировкой описывают те же ситуации; один прогон |

Требования к составу (проверяются скриптом `audit_v1/check_data.py`):

* не менее 150 диалогов в наборах A+B+C, не менее 20 из них — 8 и более реплик;
* не менее 15 % кейсов с опечатками (пропуск/замена буквы), не менее 10 — с
  неполными фразами, не менее 12 — с таджикскими вставками (`бале`, `не`,
  `хуб`, `чӣ`, `кӣ`, `ин`, `он`, `дуст`, `хона`, `kitob` …) в русской реплике;
* в каждом наборе обе стороны (связка/переспрос) представлены по категориям;
* каждый кейс — самостоятельный диалог: факты сообщаются внутри реплик
  пользователя, отдельного «предобучения» нет.

### Схема кейса

```json
{"id":"a-001","set":"bind","category":"pronoun_after_name",
 "turns":["Иван — это физик.","Кто такой Иван?","А он кто?"],
 "expected":"BIND","entity":"Иван","pronoun":"он",
 "author":"arena-auditor","date":"2026-11-27",
 "method":"автор размечает, к какому объекту отсылает местоимение в последней реплике"}
```

`expected` ∈ {`BIND`, `REFUSE`}; для `BIND` обязателен `entity` — имя, как оно
встречается в диалоге; для `REFUSE` — `refuse_reason` ∈ {`no_antecedent`,
`ambiguous`, `gender_mismatch`, `group`}.

### Второй размечающий и согласие

Второго человека у аудита нет, поэтому «второй размечающий» — это **скрипт
независимой разметки** `audit_v1/second_annotator.py`, который не читает метки
автора, а применяет к тексту диалога формальное правило:

> найти все упоминания объектов в репликах до последней; если последняя реплика
> содержит местоимение, отметить `BIND` на последнем упоминании, согласующемся
> по роду с местоимением (род — по окончанию имени: `-а/-я` → женский,
> иначе мужской), если такое единственно; если таких нет — `REFUSE`
> (`no_antecedent`/`gender_mismatch`); если их два и они равнозначны — `REFUSE`
> (`ambiguous`); для «они» — `REFUSE` (`group`).

На случайной выборке 30 % кейсов каждого набора (seed 20261129, выборка
фиксируется в `audit_v1/data/second_sample.json`) считается наблюдаемое
согласие и **каппа Коэна** между метками автора и скрипта. Это согласие
«человек ↔ формальное правило», а не «человек ↔ человек»; в отчёте это будет
написано именно так. Каппа ниже 0.4 считается слабой разметкой, и это
отражается в ограничениях.

## 3. Метрики (только раздельно)

Для набора X и стратегии S:

* **точность связки** — верных связок / n(BIND); 95 % ДИ Уилсона;
* **точность отказа** — верных отказов / n(REFUSE); 95 % ДИ Уилсона;
* **доля ошибочных связок** — связок не с тем объектом / n(BIND);
* **доля потерянных референтов** — отказов / n(BIND) (то есть цена осторожности);
* **доля необоснованных связок** — связок на кейсах `REFUSE` / n(REFUSE).

Сводной «безопасной точности» **не будет ни в одной таблице**: связки и отказы
считаются отдельно, у каждой цифры своё n и свой интервал. Для сравнения
стратегий используется только пара («точность связки», «доля потерянных
референтов») плюс точность отказа — без их смешивания.

Отказы системы определяются формально: если в последней реплике местоимение
осталось неразрешённым (`AMBIGUOUS`) или ответ содержит уточняющий вопрос —
это отказ. Привязка к классу/свойству (например, «он» → «физик») считается
ошибочной связкой, а не отказом.

## 4. Базовые стратегии (обязательны)

Реализуются в `audit_v1/baselines.py`, на тех же наборах и в тех же метриках:

1. **B1 «всегда отказывать»** — никогда не связывает; эталон нижней границы
   точности отказа и верхней границы потерь.
2. **B2 «последнее имя»** — связывает с последним именем собственным
   (слово с заглавной буквы, не первое слово реплики, не местоимение) в
   репликах до последней; если имени нет — отказ.
3. **B3 «последнее существительное нужного рода»** — связывает с последним
   именем/нарицательным, чей род (по окончанию: `-а/-я` → женский, иначе
   мужской) совпадает с родом местоимения; «они» всегда отказ.

Базовые стратегии не используют базу знаний проекта и не знают разметки.

## 5. Языковая модель (Gemma 3 270M)

Формат ответа общий для системы и модели: JSON `{"referent": "<имя>"}` либо
`{"referent": null, "clarify": true}`.

Прогрев и промпт фиксируются здесь **до** прогона; примеры из hidden-набора в
промпт не попадают (в промпте один общий пример на вымышленных именах).

```
Ты — модуль разрешения местоимений. Тебе дают диалог и последнюю реплику.
Определи, к какому объекту относится местоимение в последней реплике.
Если однозначного объекта нет — не угадывай.
Ответ — только JSON: {"referent": "имя"} или {"referent": null, "clarify": true}.
Пример: диалог «Аня — врач. Кто такая Аня? Он врач?» → {"referent": null, "clarify": true}
Диалог:
{DIALOGUE}
Ответ:
```

Требования: `temperature=0`, `top_p=1`, один и тот же формат для всех наборов,
промпт не меняется между наборами. Если Gemma 3 270M не запускается в среде
аудита (нет весов/рантайма), результат — **INCONCLUSIVE** с указанием причины;
замена другой моделью без пометки запрещена.

## 6. Порядок и правила честности

1. Коммит протокола → коммит наборов A–C, E и **запечатывание** D (sha256 в
   `audit_v1/data/SEALED.sha256`, файл не читается до финального прогона).
2. Прогон на A–C и E. Любая правка кода системы, вызванная этими наборами,
   делается **после** прогона, отдельным коммитом, с повторным прогоном и
   пометкой «после правки»; цифры «до» сохраняются в отчёте.
3. Финальный прогон на D — ровно один раз, без правок между запуском и
   записью результата.
4. В отчёте для каждой цифры: n, набор, команда, 95 % ДИ, дата и хеш коммита.
5. Никаких утверждений о «понимании языка»: вывод ограничен проверенными
   наборами.

## 7. Критерии вердикта (заранее)

Для каждого заявления C1–C7:

* **VERIFIED** — измерение на независимом наборе подтверждает заявление в его
  собственной формулировке;
* **FAILED** — измерение противоречит заявлению (например, точность связки
  ниже, чем у базовой стратегии B2/B3, или интервал не покрывает заявленную
  величину);
* **INCONCLUSIVE** — измерение невозможно (нет устройства/модели) или n
  слишком мал, чтобы различить стратегии;
* **NOT DONE** — заявление не проверялось этим аудитом.

Правило про «ценность системы»: если нижняя граница 95 % ДИ точности связки
системы **не выше** точечной оценки лучшей базовой стратегии, система не
считается выигрывающей у этой стратегии, и в отчёте это пишется прямо.
