# V016_MIGRATION_REPORT — миграция v1 → v2

Модуль: `rasm_cim_v16/migrate.py`. Схема: `LEGACY_SCHEMA_VERSION = 1` →
`SCHEMA_VERSION = 2`. Все числа ниже получены реальным запуском
`migrate_file` на файле, записанном на диск.

---

## 1. Главное ограничение (честно)

**FACT** — в этом репозитории нет ни `~/.rasm-cim/kb.json`, ни
`~/.rasm-cim/context.json`, ни кода, который их создавал бы (grep по
`kb.json|context.json|.rasm-cim|is_a` на момент аудита — ноль совпадений).

**INCONCLUSIVE** — совместимость с реальной пользовательской базой v1
непроверяема: проверять не на чем. Поэтому:

* формат v1 описан как **входной контракт** мигратора;
* все тесты работают на синтетической базе, созданной
  `write_legacy_sample()` и записанной в файл тем же модулем;
* проверка «на копии реальной базы», требуемая заданием, **не выполнена** —
  она невозможна в этом окружении.

Что проверено реально: код миграции, его идемпотентность, резервное
копирование, откат, отсутствие потерь на синтетическом входе и работоспособность
результата в живой системе.

---

## 2. Правила миграции

| Правило | Условие | Результат |
|---|---|---|
| `R1_ALIAS` | `p == "is_a"`, имя субъекта содержится в имени объекта, объект — имя собственное | `alias_of`, уверенность 0.95 |
| `R2_INSTANCE` | `p == "is_a"`, объект — нарицательное существительное | `instance_of`, уверенность 0.90 |
| `R3_PRESERVE` | `p == "is_a"`, обе стороны — имена собственные, доказательств тождества нет | `related_to`, уверенность **0.50**, флаг `identity_unknown` |
| `R4_KEEP` | `p` — известное v0.16 отношение и не `is_a` | сохраняется как есть (уверенность не повышается) |
| `R5_FALLBACK` | `p` неизвестно | `related_to`, уверенность 0.50, запись в `flagged` |
| `R6_NEGATION` | `neg` / `polarity == "false"` | `polarity = false` |
| `R7_PROVENANCE` | всегда | `source = "migration:v1"`, исходная запись сохраняется в `provenance` |

**Особый случай `is_a`, который использовался как псевдоним** (требование
задания): он разбирается правилом R1 **только при доказательстве имени** —
вхождении одного имени в другое. Если доказательства нет (R3), тождество
**не утверждается**: запись сохраняется как `related_to` с уверенностью 0.50 и
флагом, а не превращается в слияние двух разных людей. Это прямое следствие
правила «никогда не объединять сущности только из-за похожих имён».

## 3. Результат контрольного прогона

Вход — 6 записей v1, включая все спорные случаи:

```
("Ньютон",            "is_a",       "Исаак Ньютон")                    → R1
("Исаак Ньютон",      "is_a",       "физик")                           → R2
("Альберт Эйнштейн",  "is_a",       "Исаак Ньютон")                    → R3
("Исаак Ньютон",      "discovered", "закон всемирного тяготения")      → R4
("Исаак Ньютон",      "no_such_rel","что-то")                          → R5
("Ньютон",            "is_a",       "химик")                           → R2
+ entities: [{"name": "Исаак Ньютон", "aliases": ["Ньютон"]}]
```

Отчёт `migrate_file` (дословно):

```json
{"schema_in": 1, "schema_out": 2,
 "rules": {"R1_ALIAS": 1, "R2_INSTANCE": 2, "R3_PRESERVE": 1, "R4_KEEP": 1,
           "R5_FALLBACK": 1, "R7_PROVENANCE": 6},
 "records_in": 6, "records_out": 6,
 "notes": ["st-000003: legacy is_a 'Альберт Эйнштейн'->'Исаак Ньютон' kept as related_to (confidence 0.50); identity deliberately NOT asserted",
           "st-000005: legacy no_such_rel 'Исаак Ньютон'->'что-то' kept as related_to (confidence 0.50); identity deliberately NOT asserted"],
 "status": "migrated",
 "backup": "/tmp/…/kb.json.bak-20261127-024228",
 "verify_reread_statements": 6, "verify_schema": 2}
```

`flagged`:

```json
[{"record": {"s": "Исаак Ньютон", "p": "no_such_rel", "o": "что-то",
             "source": "legacy-sample", "ts": "2026-01-01T00:00:00"},
  "rule": "R5_FALLBACK", "note": "unknown relation 'no_such_rel'"}]
```

**RESULT** — `records_in == records_out == 6`: потерь нет.
**RESULT** — `verify_reread_statements == 6`: после записи файл перечитан и
сверен.
**RESULT** — резервная копия создана (`kb.json.bak-<timestamp>`).
**RESULT** — повторный запуск: `status == "already-current"`, содержимое
графa не меняется (`test_migration_is_idempotent`).
**RESULT** — `dry_run` не пишет ничего и не создаёт резервных копий
(`test_migration_dry_run_writes_nothing`).
**RESULT** — отрицания переносятся: `neg: true` → `pol: "false"`
(`test_migration_of_negated_legacy_records`).

Миграция контекста на реальном файле:

```json
{"status": "migrated", "schema_in": 1, "schema_out": 2,
 "notes": ["v1->v2: topic tracking added, 0 entities carried over"],
 "entities_kept": 0, "history_kept": 1}
```

## 4. Защитные механизмы

1. `migrate_file` **отказывается писать**, если `records_out != records_in` —
   молчаливая потеря записи невозможна.
2. Резервная копия создаётся **до** записи; `Store.rollback(backup)`
   восстанавливает файл побайтно (тест
   `test_migration_creates_a_backup_and_can_roll_back`).
3. После записи файл перечитывается, сверяются число утверждений и версия схемы.
4. Документ текущей версии не изменяется (`test_upgrade_kb_dict_on_a_current_document_is_a_noop`).
5. Документ **более новой** схемы не понижается молча
   (`test_a_newer_schema_is_not_silently_downgraded`).
6. Каждое спорное решение попадает в `notes`/`flagged` с именем правила —
   undocumented semantic changes исключены: все правила перечислены в разделе 2.

## 5. Работоспособность результата

**RESULT** — после миграции синтетической базы система отвечает на вопрос
по псевдониму:

```
Ньютон — физик?  →  DIRECT, «Да. Исаак Ньютон — физик.»
                    основание: st-000002, уверенность 0.90
```

Статус `DIRECT`, а не `INFERRED`: псевдоним «Ньютон» перенесён миграцией в
запись сущности, поэтому тождество **хранится**, а не выводится.

**RESULT** — побочный эффект старой записи `("Ньютон","is_a","Исаак Ньютон")`
при уже зарегистрированном псевдониме — утверждение `X alias_of X`. Оно
сохраняется с `status = "redundant"`: остаётся в файле и в
`stats()["redundant"] == 1`, но не индексируется и не участвует ни в одном
запросе. Самопетель в выдаче нет
(`test_migration_result_is_usable_by_the_system`).
