# PLAN v0.10 — стабильность и надёжность ядра (по §4 промпта; язык НЕ трогаем)

Принципы этапа: сначала стоимость участка, потом оптимизация; одинаковые данные и
условия, несколько повторов, изоляция процессов; PASS/PARTIAL/FAIL/INCONCLUSIVE без
повышения статуса «на глаз»; каждый шаг — маленький, тестируемый, с артефактом.
Каждый шаг заканчивается прогоном 109+40 (плюс новые tests_v10) и записью в
results_v10/ + документируемым лимитом, если цель не достигнута.

## Ш0. Гигиена воспроизводимости (полдня)
- `requirements-dev.txt` (pytest/hypothesis/atheris) + опциональный numpy — декларировать,

- `pyproject.toml` для `rasm_cim_v9` (PEP 621, без новых runtime-зависимостей) — чтобы
  `pip install -e` работал; compat-импорты v0.8 остаются файловыми, без единого пакета.
- Тест-гейт: чистая venv без пакетов даёт понятную ошибку-инструкцию, с пакетами — 40 passed.

## Ш1. Профилировочный конвейер ядра (главный выход этапа)
`bench_v10/profile_core.py`: матрица {объёмы 1k/10k/100k/1M/10M?} ×
{операции: build, open, exact get, partial get, scan, update(fsync), replay-open, compact} ×
{метрики: wall, p50/p95/**p99** (новый!), throughput, VmHWM, VmRSS-дельта,
tracemalloc peak+total аллокаций, bytes_read, cache_hits} — каждый ячейка = отдельный
подпроцесс, медиана из 5 повторов, разброс min..max наружу. Целевая платформа host; тот же
скрипт умеет `--quick` для Termux (1k/20k). Артефакт results_v10/profile_matrix.json.
Тест гейта: ни одна цифра без повторов и изоляции; p99 присутствует во всех строках.

## Ш2. Закрыть хвосты M4 (устройство; без них ядро «стабильно» только на host)
- Извлечь из сырых JSON на телефоне `v09_v3_store` / `v09_v3_journal_updates`
  (команда в README_v09.md) → вердикт ≤5 ms на FLASH: PASS/FAIL/INCONCLUSIVE.
- r3-прогон {20k,100k} → независимые RSS/peak; проверить снятие загрязнения

- Оба результата: только в `results_v10/device/` (или results_v9/device/ для r2-наследия),
  никогда в host-таблицы.

## Ш3. Стоимость длинного журнала и точка compact (известная регрессия v0.9)
- Кривые: open-время vs #кадров {1..10 000} × размер-кадра {1..256} @ {10k, 100k, 1M}
  (host); сейчас 60 кадров @1M = +0.29 s, compact 1.45 s — понять формулу (O(#кадров) walk
  + sorted merge?).
- Кандидаты (только если кривая показывает практическую боль): (a) кэш last_seq в хвосте
  файла с CRC-валидацией; (b) forced-compact-политика (порог N кадров/K байт) — конфиг,
  не магия; (c) батч-реплей журнала при открытии. Каждый кандидат = A/B + регрессии,
  проигравший остаётся с объяснением.
- Матрица краж-инъекций расширяется: **SIGKILL во время compact** (дыра Ш0-аудита 4.4),
  во время forced-compact, при записи хвост-кэша (если появится) — восстановление обязано
  дать старый или новый валидный вариант, не гибрид.

## Ш4. Надёжность записи/политика fsync (из Ш2 данных устройства)
- Если устройствый upd p95 > 5 ms: измерить batch-commit (fsync раз в K транзакций +
  корректные гарантии R3.2 для хвоста) + документ «что теряется при power loss».
  Режим per-txn остаётся default-safe; batch — opt-in с явной оговоркой в README.

## Ш5. Прочее усиление ядра (по остаточному приоритету)
- Корректность на испорченном входе — расширить fuzz-матрицу: открытые файлы v1/v2 с
  битыми хвостами; partial-page в index-страницах; replay идемпотентность при
  пересечении кадров и compact (новые atheris-цели на compact-путь).
- Проверка лимитов ресурсов: EMFILE-friendly `with`-протокол у V3Store (закрыть fd при
 Collectors; сейчас зависимость от явного close()), context-manager тест.
- sidecar-индекс (открытый вопрос v0.9 PLAN_v1.0 п.4): реализовать только как cache с
  инвалидацией (base crc+size), замерить open 0.29→?, при отказе — оставить запись.
- p95≤2×dict остаётся структурным FAIL: переизмерить в Ш1 с p99, не трогать код ради статуса.
