# RASM-CIM v0.7 — Full Rust Compute Core: Отчёт
Дата: 2026-11-25. Инструменты: rustc/cargo 1.100.0 stable, CPython 3.13.18,
numpy 2.3.5, matplotlib 3.11.2. Хост: Linux x86_64, 2 CPU, 1.9 GiB RAM.

## 0. Итог одним абзацем

Вычислительное ядро RASM-CIM (RNS, иерархическая память, TruthGraph, КА,
резервуар, BFS-синтез, packed-хранение, бинарный формат) перенесено в Rust
без `unsafe` (`#![forbid(unsafe_code)]`, проверка: пробный unsafe-блок вызывает ошибку компиляции); Python-биндинги PyO3 работают; математическая эквивалентность
подтверждена 28 cross-language тестами и property/fuzz-тестами (≈7·10^5
проверок), градиенты обучения — finite-difference проверкой по ВСЕМ
параметрам. На идентичных данных и алгоритмах Rust быстрее в 1.2–14 раз по
медиане (9 наборов из 10 ≥ 1.7×; partial-query p95 = 0.8× — Rust медленнее
в хвосте, сохранено). Ни один результат экспериментов v0.1–v0.6 не изменён;
REFUTED-гипотезы воспроизведены как отрицательные и в Rust. Android: сборка
кода для aarch64-linux-android подтверждена (ELF ARM aarch64), замера на
устройстве не было — поддержка Android НЕ объявлена завершённой.

## 1. Обязательный аудит (§1 ТЗ)

`docs/AUDIT_v0.1-v0.6.md` — составлен ДО кода: карта зависимостей версий,
таблица «компонент Python → модуль Rust», отсечение Python-специфичных
библиотек (sklearn/matplotlib/демо остаются в Python), список известных
ошибок и ограничений. Что реально нуждалось в Rust: целочисленное ядро
(RNS/КА/граф/packed-хранение/BFS) — подтверждено замерами v0.5–v0.6
(Python-интерпретатор = бутылочное горлышко при N≥10^4). Что не нуждалось:
 plotting, сравнительные таблицы LLM, датасет-пробы sklearn
(см. `docs/NON_PORTED_v0.7.md`).

## 2. Реализация (структура — `docs/ARCHITECTURE.md`)

39 модульных файлов в crate; 0 `unsafe`; зависимости: thiserror, rayon,
rand (+criterion dev). serde удалён как неиспользуемый (аудит-предупреждение
компилятора — не заглушен, а устранён). Tokio не добавлен: асинхронного
I/O в ядре нет (обоснование в архитектуре, §2 таблицы решений).

## 3. Перенесённая функциональность (§3 ТЗ)

| Компонент | Rust | Эквивалентность |
|---|---|---|
| RNS: encode/decode, add/sub/mul, range checks, signed, CRT, учёт ops | `src/rns` | точная (включая границы 0/M−1, переполнение → ValueError, непарные moduli → ошибка) |
| Memory: exact/partial/noisy/semantic/episodic/procedural, dedup, CONFLICT, сжатие RNS, калибровка tau | `src/memory` | точная для всех детерминированных путей; ядро noisy-поиска сверяется с инъецированными HV (RNG-стримы намеренно разные) |
| Arch-A / Arch-B / Arch-C | `src/architectures/*` | независимые прототипы, НЕ объединены (запрет §11); числа v0.6 воспроизведены: sparse 9 vs dense 64, candidates 238 |
| Compute core: PackedStore 16 B/запись, batch, rayon | `src/compute` | байт-в-байт с `struct.pack("<qq")` (тест) |
| Reservoir (шаги динамики) | `src/ca` | порт; числа обучения не переносились (readout ridge остался в Python — обосновано) |
| Learning: TanhRNN-BPTT + selective SSM + Adam | `src/learning` | формулы — построчно из Python; градиенты верифицированы (см. §7) |
| Бинарный формат v1 | `src/storage` | serialize/deserialize + header-partial-read + импорт Python-bytes; повреждение → Err (FNV-1a) |

## 4. Соблюдение технических требований (§4)

stable ✓; безопасные структуры по умолчанию ✓; переиспользование буферов
(кадр CA, единый Vec у PackedStore) ✓; целочисленная арифметика без float в
RNS/CA ✓; cache-friendly: плоские Vec, row-major матрицы обучения ✓;
zero-copy: там, где осмысленно (срез payload в deserialize читается
`chunks_exact` без копирования записей до проверки); SIMD: НЕ добавлен —
измеримого преимущества на ядре нет (кадр CA уже 1.9 мкс; граница PyO3
доминирует), запрет «SIMD только при измеримом выигрыше» выполнен молчанием;
rayon: применён, с отрицательным результатом на put (§6); criterion: 15
бенч-кейсов; `unsafe` нет → отдельных safety-тестов не требуется (фокус
смещён на fuzz по десериализации — п. 7).

## 5. Python-совместимость (§5)

`bindings/python/` → cdylib `rasm_cim_ext.so` (PyO3 0.23, abi3-py38). Python
передаёт данные (Vec<i64>/list), получает результаты, работает со stores,
вызывает вычисления (RNS/память/КА/синтез/хранение/обучение), запускает
бенчмарки (benchmarks/run_bench.py --side rust) и сверяет с Python-эталонами.
Исходные Python-версии v0.1–v0.6 не тронуты; регресс pytest v0.6 (7/7)
зелёный после всех изменений.

## 6. Бенчмарки производительности (§6) — измерено, не заявлено

Методика: 10 наборов, идентичные данные на обе стороны, каждый замер —
изолированный подпроцесс (атрибуция VmHWM-RSS), 15 повторов, 3 прогретых
отброшены, медиана+p95 по репитейлам; время компиляции исключено (отдельный
шаг); стоимость конверсии Python↔Rust ВКЛЮЧЕНА в цифры Rust (это честная
цена вызова). Данные: `results_v7/bench_v7.json`, графики `plots_v7/`.

Медианы (release, .so через PyO3):

| Набор | Python | Rust | ratio med / p95 |
|---|---|---|---|
| RNS enc+dec 2000 | 9.98 ms | 1.043 ms | 9.6× / 11.8× |
| Memory build 5000 writes | 81.6 ms | 5.78 ms | 14.1× / 10.0× |
| Partial 97 queries | 0.235 ms | 0.195 ms | 1.20× / **0.84×** |
| Noisy 200 q (D=256) | 181.2 ms | 56.5 ms | 3.2× / 3.0× |
| Graph 2000 lookups | 1.554 ms | 0.917 ms | 1.7× / 1.5× |
| CA dense 200×1024 | 3.83 ms | 1.90 ms | 2.0× / 2.3× |
| CA sparse 200×1024 | 5.49 ms | 2.03 ms | 2.7× / 2.1× |
| BFS synthesis 238 cands | 0.527 ms | 0.097 ms | 5.4× / 4.8× |
| PackedStore 50k put | 22.4 ms | 10.7 ms | 2.1× / 2.4× |
| Batch get 50k | 13.5 ms | 5.78 ms | 2.3× / 2.5× |

Отрицательные/ограничивающие результаты (сохранены):
- **partial_memory p95 < 1×**: в хвосте распределения Rust на этом хосте
  медленнее (2 CPU, шум планировщика). Единственный тест ≠ вывод; вывод
  строится по всем 10 наборам.
- **rayon batch-put 0.87× медленнее последовательного** (50k пар, 2 CPU);
  batch-get 1.29× быстрее. Параллелизм полезен не везде — измерено.
- **RAM**: выигрыш есть только там, где данные велики относительно
  интерпретатора: exact_memory 43.5→34.7 MiB; в лёгких наборах RSS на
  уровне шума интерпретатора Python; batch_ops RSS Rust ВЫШЕ (47.9 vs
  44.7 MiB) из-за двух аллокаций батчей в одном процессе. 16 B/запись —
  свойство структуры данных, не процесса.
- **CPU** (os.times user+sys) записан в JSON для каждого замера.
- **Количество аллокаций**: не измерялось (нет профиливщика) — отмечено как
  NOT MEASURED, не оценено расчётом.
- **Debug vs Release** (тот же бенч-код): rns 11.6 vs 9.7 ms, CA200 3.28 vs
  2.01 ms, synth 0.124 vs 0.075 ms; кандидаты 238 в обоих — профиль
  оптимизации меняет скорость, не результат.

Criterion (микро, только Rust; 15 кейсов): RNS encode 2000 = 57 мкс (35 Melem/s);
add+mul 140 мкс; memory build 1k/10k/100k = 0.67/7.9/135 мс; partial
100k = 1.23 мс; CA dense 1.88 мкс/кадр 1024; parity 0.89 мкс;
serialize/deserialize 50k = 1.13/1.09 мс; packed put 50k = 2.0 мс;
synth len3 = 39.8 мкс.

Масштабирование (log-log, `plots_v7/scaling.png`): обе стороны линейны по N
(1k→100k: Python RNS enc 3.2→290 мс ≈ 91×, Rust 0.48→35 мс ≈ 73×; наклон
≈1.06 vs 1.00 в лог-лог — оба O(N)); Rust выигрывает константу, не
сложность. **Это не доказательство масштабируемости архитектуры — это
доказательство константной реализации.**

## 7. Тестирование корректности (§7)

- Rust unit: 32 теста (каждый модуль). Property/fuzz-style: 6 тестов,
  ≈7·10^5 проверок (RNS по 4 наборам moduli × 20k, add/sub/mul × 20k,
  CRT против наивной формулы × 9k, модельная эквивалентность PackedStore,
  200k случайных байтовых «супов» в десериализатор — ни одного паника,
  5k инвертированных битов — все пойманы чексуммой, граф 50k случайных
  assert/retract).
- Cross-language pytest: 28 тестов против реальных Python-ссылок (rns4,
  memory_system v0.6, compute_core, ca4, program4, graph4, ssm3,
  selective_ssm) с проверяемой точностью: бит-в-бит (байты, программы,
  числа кандидатов), 1e-9 (логиты при инъецированных весах), конечные
  разности (gradcheck по ВСЕМ 29 параметрам каждой модели: макс. rel-ошибка RNN 8.8e-8,
  SSM 8.3e-8 (пример `examples/gradcheck.rs` прогоняет полный sweep)).
- Граничные случаи: 0/M−1/M, signed −M/2±1, пустые данные, дубликаты,
  конфликты, неизвестные ключи, обрезанные/повреждённые файлы,
  многопоточность (threads в Python над независимыми store'ами,
  параллельные батчи → идентичные результаты).
- «Unit-тесты ≠ доказательство скорости»: скорость отдельно (§6),
  корректность отдельно (§7).

## 8. Мобильная версия (§8)

Целевые профили реализованы (mobile: 1 поток, параллелизм выключен, бюджет
256 MiB; desktop 4; server без ограничения). Сборка для
aarch64-linux-android: `cargo check` и `cargo build --lib --release` —
ОК, внутри rlib объекты подтверждены `ELF 64-bit LSB relocatable, ARM
aarch64`; линковка бинарника требует NDK (отсутствует в песочнице —
задокументировано, не имитировано). aarch64-apple-darwin и
x86_64-pc-windows-msvc: compile-checked (cargo check), рантайм-тестов нет —
не заявляем. Инструкции Termux + матрица: `mobile/TERMUX.md`.
Потоковое чтение базы (mobile «не грузить всё в RAM») НЕ реализовано —
запланировано в v0.8 M2 как единственное незакрытое требование §8.
**Android-поддержка не объявлена завершённой** (нет теста на устройстве).

## 9. Формат хранения (§9)

Версионируемый (magic RASM + u32 version=1), целостность (FNV-1a на payload),
безопасная десериализация (fuzz-тест), частичное чтение заголовка (count
без payload), обновление = rewrite payload (задокументировано, atomicity нет
— честно), импорт/экспорт байтов Python PackedStore (бит-идентичность
тестируется). Поток записей — те же 16 B на факт, что у v0.6.

## 10. Научная проверка (§10) — отдельно реализация, отдельно архитектура

| Ось | Результат |
|---|---|
| Производительность реализации | Rust ядро быстрее на 1.2–14× (медианы, §6); отдельные точки медленнее (p95 partial, rayon put) |
| Эффективность алгоритма | НЕ изменилась: те же 238 кандидата BFS, те же N/97 частичных операций, та же линейная масштабируемость |
| Качество решений | Идентично: те же программы, TRUE/CONFLICT/UNKNOWN статусы, те же accuracy=1.0 на v0.6-задачах |
| Память | −8…−11 MiB там, где структура доминирует; 16 B/запись; шум в лёгких наборах |
| Масштабируемость | Линейность подтверждена на 1k→100k в обеих реализациях; дальше — экстраполяция, не доказательство |

RNN/selective-SSM parity в Rust на своих инициализациях: 0.505 vs 0.500
(шанс 0.5) — L1 остаётся REFUTED; эксперимент не донастроен до «успеха».
Отрицательные результаты §6 сохранены в таблицах и графиках. Снижение RAM
не трактуется как рост «интеллекта».

## 11. Соблюдение запретов (§11)

Python не удалён и не изменён (регресс 7/7); A/B/C не переписаны и не
слиты; заглушек нет (все модули имеют рабочие тесты;learning содержит
полный BPTT+Adam с gradcheck); измерения — wall-clock/RSS, не расчёт;
утверждение «Rust быстрее» подкреплено 10 наборами с разбросом; CAM
остался софтверной моделью; compute-in-memory — моделью; RAM-выигрыш ≠
интеллект; слияния архитектур нет; Android не объявлен; результаты
экспериментов Rust не менял (числа совпадают с v0.6); все отрицательные
результаты в отчёте; `unsafe` — 0 (`#![forbid(unsafe_code)]`; проверено вживую: пробный unsafe-блок не компилируется).

## 12. Что найдено по ходу (кратко; полностью — docs/ERRORS_FOUND_v0.7.md)

15 позиций: 6 ошибок порта (CRT-редукция, BPTT off-by-one, Adam
размер, мёртвые зависимости, 2 бага харнеса) — все найдены тестами и
исправлены; 4 предсуществующих quirks Python, сохранённых как есть (таблица
rule-110 НЕ соответствует каноническому 110 — найдено при порте; семантика
retract; отсутствие функционального вывода при явном o; зависимость ops
sparse-КА от кластеризации активности).

## 15. Вывод v0.7

Rust-ядро даёт измеримый 2–14× выигрыш реализации на идентичной семантике
без единого изменения научных результатов, переносимо на ARM64-цели
(компиляция подтверждена; on-device впереди), и вскрывает при переносе 4
семантических долго-наследованных расхождения Python-оригинала. Это не
«умнее», это быстрее и строже.
